    chr1–22 parity at release 116¶

    Date: 2026-07-28 Scope: vepyr vs Ensembl VEP 116 CSQ parity, merged cache, --everything --hgvs, HG002 GRCh38, all 22 autosomes.

    Supersedes the chr22-only picture in 2026-07-28-motif-parity-handover.md.

    Where things stand¶

    First full chr1–22 run at release 116 — the earlier work had only ever been measured on chr22.

    field mismatches 31,699 734

    Structure was already exact before this session: every variant produced the same number of CSQ entries in the same order. Only field values differed.

    What landed¶

    Three commits, all measured against the release-116 reference rather than inferred:

    1. bio-formats e5d63b5 — feat(ensembl-cache): extract BindingMatrix elements and motif sequence. Three typed MotifFeature columns: binding_matrix_elements (frequencies flattened to A,C,G,T per position, positions joined by ;), binding_matrix_unit, motif_seq. All three were already inside raw_object_json; none had a typed column. The elements column dictionary-encodes to almost nothing — a whole cache draws on 51 distinct matrices.

    2. bio-functions c96d57f — feat(vep): compute HIGH_INF_POS and MOTIF_SCORE_CHANGE. New motif_matrix.rs implementing Ensembl's chain: frequencies → probabilities (pseudocount 0.1) → weights (log2(p/0.25)) and bits (p * (2 - H)); is_position_informative (>1.5 bits, true SNPs only); relative_sequence_similarity_score; motif_score_delta. Also adds binding_matrix_length to the context-scan projection, where it had been left out — MOTIF_POS was silently falling back to the motif span there.

    3. bio-functions 24f1807 — fix(vep): emit TFBS_ablation for deletions that remove a motif. VariationEffect::feature_ablation is complete_overlap_feature and deletion and applies to ordinary sequence variants, not only structural ones — which is the only place vepyr read it.

    4. vepyr bb37297 — build_cache_entity() plus the targeted entity rebuild workflow, now named e2e-testing/scripts/rebuild_cache_entity.py.

    Validating before committing to Rust¶

    The scoring chain was modelled in Python first and scored against the VEP reference directly: 1,771 of 1,771 MotifFeature CSQ entries on chr1 and chr22 agreed on both fields before a line of the Rust was wired up. The two engine tests are anchored on real VEP 116 output (chr22:17037897 forward strand, chr22:17088127 reverse strand).

    Rebuilding one entity instead of the whole cache¶

    A MotifFeature schema change used to mean a 90-minute, 36 GB full rebuild to refresh 83 MB of motif shards. The motif mode of rebuild_cache_entity.py does it in 1.9 minutes, staging into <cache>.motif-rebuild and verifying every column is populated before the swap:

    uv run python e2e-testing/scripts/rebuild_cache_entity.py \
    --release 116 --cache-type merged --entity motif            # dry run
uv run python e2e-testing/scripts/rebuild_cache_entity.py \
    --release 116 --cache-type merged --entity motif --run

    What is left, and why¶

    1. HGVSc / HGVS_OFFSET — rule decoded from the 116 source¶

    The largest remaining class (292 + 98). vepyr emits nothing where VEP emits a value in 178 of 179 sampled cases. The rule is in TranscriptVariationAllele::_var2transcript_slice_coords (line 2683 of the 116 image) and it is clamping, not bailing:

    my $tr_length = $tr_end - $tr_start + 1;
# Variant is entirely before or after transcript
return undef if (($vf_start < 1 && $vf_end < 1) || ($vf_start > $tr_length && $vf_end > $tr_length));
# Clamp coordinates to transcript boundaries
my $clamped_start = ($vf_start < 1 ? 1 : $vf_start > $tr_length ? $tr_length : $vf_start);
my $clamped_end   = ($vf_end   < 1 ? 1 : $vf_end   > $tr_length ? $tr_length : $vf_end);

    $vf_start/$vf_end are transcript-slice coordinates, strand-flipped for reverse-strand transcripts (($tr_end - $_) + 1, with start/end swapped). A second guard in hgvs_transcript (line 1472) then discards the result when 3'-shifting pushes it past the slice:

    return undef if (($self->{_slice}->end - $self->{_slice}->start + 1) < ($self->{_slice_end} + $offset_to_add));

    Together these reproduce all four measured cases exactly:

    variant transcript slice coords offset guard VEP
    chr22:20890758 CAAAAAAAA>C ENST00001129240 +1, len 31813 31813–31813 14 31813 < 31827 → undef (empty) ✓
    chr22:26665247 AAAAG…>A ENST00000717199 +1, len 7736 7734–7736 27 7736 < 7763 → undef (empty) ✓
    chr22:23658088 CTCCTCT>C ENST00000417194 −1, len 35092 35092–35092 0 passes n.5004del ✓
    chr22:42720811 GCGGC…>G ENST00000483026 −1, len 26859 1–18 0 passes n.1_18del ✓

    Note the last row: n.1_18del falls straight out of the clamp. That is why the earlier clip attempt regressed — it got the clamping right in spirit and wrong in six specifics:

    # Ensembl 116 vepyr / the reverted attempt
    1 Bails only when the variant is entirely outside the transcript Bails whenever either end is outside
    2 Clamps every variant class Guard applies only to deletions (ref != "-" && alt == "-")
    3 Clamps in transcript-slice coordinates, strand-flipped for strand < 1 Clipped in genomic coordinates, so reverse-strand transcripts keep the wrong end of the allele
    4 Never trims the allele; re-extracts ref from $self->{_slice}->seq() at the clamped coords, then _clip_alleles Truncated the input REF string by byte offset
    5 Discards the result when slice_len < clamped_end + shift_offset No equivalent guard — the source of the two over-emissions and both new HGVS_OFFSET mismatches
    6 Applies the 3' shift to the clamped coords (_slice_start + offset) Dropped the shift entirely on the clipped path

    Difference 5 is the one that turns this from "clip and win" into a net regression, and it is also why HGVS_OFFSET moves with HGVSc: when VEP declines, it emits neither.

    Implementing it: the blocker is vepyr's shift representation, not the clamp¶

    Both faithful readings of the rule were built and measured. Neither holds up, and the reason is structural.

    Attempt A — clamp the unshifted span, then apply the slice guard. Measured: chr1 60 → 55, chr22 10 → 10. The whole gain is the guard suppressing over-emitted HGVS_OFFSET, which is a real correctness win. But it also turns at least one empty into a wrong value: chr1:9234724 went from '' to c.-329_-315del where VEP says c.-315del. The 15-base span is the shift's display interval, which reaches back before the transcript start — the guard ran before the shift was substituted and so never saw it.

    Attempt B — clamp the shifted span instead. Fails two ways: the decline semantics vanish (when the shift pulls the span back inside the transcript the boundary test no longer fires, so the poly-A cases VEP refuses get reported), and it regresses the existing test_format_hgvsc_uses_shifted_coordinates_for_exonic_deletions.

    The two are not interchangeable because Ensembl and vepyr represent shifting differently:

    shift representation
    Ensembl 116 clamp the unshifted variant to the transcript, then add the shift as an offset in slice coordinates (_slice_start + offset), declining if that runs past the slice
    vepyr materialise the shift into a genomic display interval (HgvsGenomicShift::display_start/display_end) and substitute it wholesale inside format_hgvsc_fallback

    At a transcript boundary those differ: "clamp, then offset" cannot be expressed by clamping either the pre-shift or the post-shift genomic span, because the clamp must bound the result after the offset while the offset is measured from the clamped origin. Closing this needs the shift carried as a slice-space offset applied after clamping — a rework of how HgvsGenomicShift is consumed in format_hgvsc_fallback, not a guard bolted onto either end.

    Both attempts were reverted; the tree stays at the verified 734.

    A second, smaller HGVSc shape is unrelated to the boundary question — a coordinate offset in repeats, e.g. chr11:1094638 where vepyr says NM_002457.5:c.4396_4416del and VEP says c.4443_4463del (same length, 47 bases apart). That one is a genuine 3'-shift disagreement.

    Recording the cache release turned out to be a prerequisite nobody had met: release-116 caches ship an info.txt with no version line at all, so cache_version sat at "unknown". Detection works without a rebuild by reading the release from the cache directory name (116_GRCh38_merged). Both that and the clamping groundwork are parked, not deleted:

    branch what it holds
    wip/hgvs-transcript-clip-116 (bio-functions) release detection, TranscriptConsequenceEngine::with_cache_release, the (wrong) genomic-coordinate clip
    wip/cache-version-metadata (bio-formats) bio.vep.cache_version in schema metadata, CacheInfo directory-name fallback

    One measurement caution: after maturin develop, a comparison launched in the same shell invocation can still run against the previous extension module. A chr22 measurement read 12 immediately after a rebuild and 10 on both re-runs. Re-run before believing a delta.

    2. CLIN_SIG — 112 mismatches from 3 variants, divergence is downstream of allele matching¶

    VEP matches a colocated record via Utils/Sequence.pm::get_matched_variant_alleles, keyed on "$ref\_$alt\_$pos" after minimising both sides with trim_sequences, trying both trim directions whenever either allele is longer than 1 bp. compare_existing returns undef when that yields no matches, and the record is dropped.

    vepyr's port of that function is faithful — same key, same both-direction trimming (allele.rs::get_matched_variant_alleles), and compare_existing_variant_alleles returns None on no match. Working the chr15 case by hand, neither side matches under either rule:

    minimised key
    input chr15:89333596 T>TTGC -_TGC_89333597
    cache repeat record, alt TGC (left-trim) TGCTGC…(30)_-_89333600
    cache repeat record, alt TGC (right-trim) TGCTGC…(30)_-_89333597

    So the defect is not in allele matching. The leading hypothesis is ColocatedCacheEntry::matches_output_allele:

    self.matched_alleles.is_empty() || self.matching_allele(output_allele, ...).is_some()

    is_empty() is meant to admit unknown-allele records (no /, matched on coordinates alone), but it also admits any known-allele entry that reached the sink with an empty match list. The emitted value — conflicting_classifications_of_pathogenicity — is exactly the term the repeat record carries under the label TGC: in its clin_sig_allele, which is what a label-only match would pick. Unverified: confirm whether that entry actually arrives with matched_alleles empty before changing anything.

    3. Consequence / IMPACT / HGVSp residual¶

    The remaining shapes are the known incomplete-terminal-codon and frameshift classes, already filed: fn#130, fn#112. Examples: frameshift_variant&stop_lost where VEP says stop_lost; inframe_insertion&stop_retained_variant where VEP says stop_retained_variant.

    Gotchas added to the earlier list¶

    1. A full-genome run writes ~4.8 GB of intermediates per contig and never cleans them up. 22 contigs is ~105 GB against ~89 GB free. Delete results/116/fast_chrN/{vep,vepyr_parquet}_chrN_merged.vcf once that contig's report JSON appears — the report is only written after the comparison finishes, so it is a safe trigger.
    2. binding_matrix is not always blessed. The first row referencing a matrix carries a {"__class":..,"__value":..} wrapper; alias-resolved copies are the bare object. Probing binding_matrix.__value.elements finds the PWM on ~10% of rows and misses it on the rest. json_unwrap_blessed already handles both — bypass it and you will conclude, wrongly, that the cache is missing most of its matrices.
    3. The motif column list lives in three places (two MotifFeature loaders plus the scan_context_entity call). The compiler catches the loaders when the struct gains a field; it does not catch the projection lists, and a missing projection silently yields empty columns.

    Reproducing¶

    uv run python e2e-testing/scripts/run_comparison.py \
    --release 116 --profile merged --force --isolate \
    --no-normalize --vcf ~/workspace/data_vepyr/HG002_normalized.vcf.gz

    About an hour for all 22 contigs. Per-contig reports land in e2e-testing/reports/.
