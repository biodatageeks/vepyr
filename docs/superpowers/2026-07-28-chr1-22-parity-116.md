## What landed

Three commits, all measured against the release-116 reference rather than inferred:

1. **bio-formats `e5d63b5`** — `feat(ensembl-cache): extract BindingMatrix elements and motif sequence`.
   Three typed MotifFeature columns: `binding_matrix_elements` (frequencies flattened to
   `A,C,G,T` per position, positions joined by `;`), `binding_matrix_unit`, `motif_seq`.
   All three were already inside `raw_object_json`; none had a typed column. The elements column
   dictionary-encodes to almost nothing — a whole cache draws on **51 distinct matrices**.

2. **bio-functions `c96d57f`** — `feat(vep): compute HIGH_INF_POS and MOTIF_SCORE_CHANGE`.
   New `motif_matrix.rs` implementing Ensembl's chain: frequencies → probabilities (pseudocount
   0.1) → weights (`log2(p/0.25)`) and bits (`p * (2 - H)`); `is_position_informative` (>1.5 bits,
   true SNPs only); `relative_sequence_similarity_score`; `motif_score_delta`.
   Also adds `binding_matrix_length` to the context-scan projection, where it had been left out —
   MOTIF_POS was silently falling back to the motif span there.

3. **bio-functions `24f1807`** — `fix(vep): emit TFBS_ablation for deletions that remove a motif`.
   `VariationEffect::feature_ablation` is `complete_overlap_feature and deletion` and applies to
   ordinary sequence variants, not only structural ones — which is the only place vepyr read it.

4. **vepyr `bb37297`** — `build_cache_entity()` plus `e2e-testing/scripts/rebuild_motif_entity.py`.

### Validating before committing to Rust

The scoring chain was modelled in Python first and scored against the VEP reference directly:
**1,771 of 1,771** MotifFeature CSQ entries on chr1 and chr22 agreed on both fields before a line
of the Rust was wired up. The two engine tests are anchored on real VEP 116 output
(chr22:17037897 forward strand, chr22:17088127 reverse strand).

### Rebuilding one entity instead of the whole cache

A MotifFeature schema change used to mean a 90-minute, 36 GB full rebuild to refresh 83 MB of
motif shards. `rebuild_motif_entity.py` does it in **1.9 minutes**, staging into
`<cache>.motif-rebuild` and verifying every column is populated before the swap:

```bash
uv run python e2e-testing/scripts/rebuild_motif_entity.py            # dry run
uv run python e2e-testing/scripts/rebuild_motif_entity.py --run
```

## What is left, and why

### 1. `HGVSc` / `HGVS_OFFSET` — a release behaviour change, rule not yet pinned down

The largest remaining class (292 + 98). Deletions that overhang a transcript boundary:

| | |
|---|---|
| variant | `chr10:132397163 CCGGCGG>C` (6 bases deleted, 132397164–132397169) |
| transcript | `ENST00000631148`, starts at 132397168 — only 2 deleted bases are inside |
| **VEP 115** | `HGVSc` empty |
| **VEP 116** | `ENST00000631148.3:c.-32_-31del` |

Confirmed on the same variant in both local references, so this is a release behaviour change,
not a vepyr bug. `format_hgvsc_inner` bails deliberately and its comment cites the 115 behaviour.

**An attempt to close it was implemented, measured, and reverted.** The obvious rule — clip the
deletion to the transcript and report HGVS on the overlap, gated on the cache release — is
*wrong*. Measured on chr22 it fixed both known cases and broke two others, for a net regression
(10 → 12):

| variant | vepyr (clipping) | VEP 116 |
|---|---|---|
| `chr22:23658088 CTCCTCT>C` | `ENST00000417194.5:n.5004del` | `ENST00000417194.5:n.5004del` ✓ |
| `chr22:42720811 GCGGC…>G` | (fixed) | `ENST00000483026.2:n.1_18del` ✓ |
| `chr22:20890758 CAAAAAAAA>C` | `ENST00001129240.1:c.*3017del` | *(empty)* ✗ |
| `chr22:26665247 AAAAG…>A` | `ENST00000717199.1:n.511_513del` | *(empty)* ✗ |

VEP 116 clips in some cases and declines in others, and the split is not "which end overhangs":
`chr1:16215419` overhangs the low-coordinate end of a reverse-strand transcript and is still
clipped. chr1's 38 stayed at 38 — the clip fired 25 times there and produced nothing usable.

**Next step is to read the Perl, not to infer from more examples** — exactly the trap gotcha 6
warns about. Start at `TranscriptVariationAllele::hgvs_transcript` and the cDNA coordinate
mapping beneath it in the 116 image.

Two things worth keeping from the attempt, parked on local branches rather than deleted:

| branch | what it holds |
|---|---|
| `wip/hgvs-transcript-clip-116` (bio-functions) | release detection off the cache, `TranscriptConsequenceEngine::with_cache_release`, the clip itself |
| `wip/cache-version-metadata` (bio-formats) | `bio.vep.cache_version` in schema metadata, plus a `CacheInfo` fallback that reads the release from the cache directory name |

Recording the release turned out to be a prerequisite nobody had met: release-116 caches ship an
`info.txt` with **no version line at all**, so `cache_version` sat at "unknown". Detection also
works without a rebuild by reading the release from the cache directory name
(`116_GRCh38_merged`), which is what the parked branch ends up doing.

One more caution learned here: after `maturin develop`, a comparison run launched in the same
shell invocation can still execute against the previous extension module. A chr22 measurement
read 12 immediately after a rebuild and 10 on both re-runs. Re-run before believing a delta.

A second, smaller `HGVSc` shape is unrelated to the boundary question — a coordinate offset in
repeats, e.g. `chr11:1094638` where vepyr says `NM_002457.5:c.4396_4416del` and VEP says
`c.4443_4463del` (same length, 47 bases apart). That one is a genuine 3'-shift disagreement.

### 2. `CLIN_SIG` — colocated matching too loose on insertions

112 mismatches from **3 variants**, in both directions.

`chr15:89333596 T>TTGC` is an insertion of `TGC` at 89333597 (VEP-style: start 89333597, end
89333596, `-/TGC`). The cache holds a repeat record at **89333597–89333629** whose allele string
is a 33-mer reference with shorter alternatives, and whose `clin_sig_allele` contains
`TGC:conflicting_classifications_of_pathogenicity`. vepyr matches it on the allele alone and
reports that term; VEP does not match it, because the record's end (89333629) is nowhere near the
variant's (89333596).

`chr14:74506880 C>CGCGCGCAT` fails the other way — VEP reports `benign`, vepyr reports nothing —
so the matching is both too loose and too tight. Worth reading
`Utils/Sequence.pm::get_matched_variant_alleles` before touching it.

### 3. `Consequence` / `IMPACT` / `HGVSp` residual

The remaining shapes are the known incomplete-terminal-codon and frameshift classes, already filed:
[fn#130](https://github.com/biodatageeks/datafusion-bio-functions/issues/130),
[fn#112](https://github.com/biodatageeks/datafusion-bio-functions/issues/112).
Examples: `frameshift_variant&stop_lost` where VEP says `stop_lost`;
`inframe_insertion&stop_retained_variant` where VEP says `stop_retained_variant`.

## Gotchas added to the earlier list

7. **A full-genome run writes ~4.8 GB of intermediates per contig and never cleans them up.**
   22 contigs is ~105 GB against ~89 GB free. Delete
   `results/116/fast_chrN/{vep,vepyr_parquet}_chrN_merged.vcf` once that contig's report JSON
   appears — the report is only written after the comparison finishes, so it is a safe trigger.
8. **`binding_matrix` is not always blessed.** The first row referencing a matrix carries a
   `{"__class":..,"__value":..}` wrapper; alias-resolved copies are the bare object. Probing
   `binding_matrix.__value.elements` finds the PWM on ~10% of rows and misses it on the rest.
   `json_unwrap_blessed` already handles both — bypass it and you will conclude, wrongly, that the
   cache is missing most of its matrices.
9. **The motif column list lives in three places** (two `MotifFeature` loaders plus the
   `scan_context_entity` call). The compiler catches the loaders when the struct gains a field; it
   does **not** catch the projection lists, and a missing projection silently yields empty columns.
