# Polars integration on vepyr 0.11.0 (chr22, merged cache)

Results behind the vepyr paper's Polars numbers on vepyr 0.11.0: supplement Section 8.3
(Table 18, worker sweep), Section 8.5 (Tables 19-28; Figures 4, 6 and 7) and the numbers of
main-text Figure 1D. Measured on 2026-11-21 on an Apple M3 Max (16 cores), macOS 15.7.9,
Python 3.12.2, vepyr 0.11.0 from PyPI, Polars 1.44.2, polars-bio 0.38.0 (`env.json`).

## Harness

The harness that produced this directory is `performance-tests/polars-integration/` (`pibench/`,
`scripts/`, `panels/`). The run used it at commit `e5947c8` of branch
`perf/polars-integration-harness` ("perf: Polars integration benchmarks for the paper supplement
(vepyr 0.10.0)"); these directories on master are identical to that commit. `run.sh` here expects to
sit in that tree (it `cd`s three levels up to `performance-tests/polars-integration`). The two
scripts specific to this run, `equiv.py` and `run_filter_only_polars.py`, are kept in this directory.

The 0.10.0 run directory that `run.sh` reads as `$OLD`
(`performance-tests/polars-integration/outputs/116/macos_Mareks-MacBook-Pro_chr22_merged_v0100`) is
not on master: it stays on branch `perf/polars-integration-harness` at `e5947c8`. The stages
`prepare` and `e2e` need it. Everything this run reuses from it is copied here (next section).

## VEP side reused from 0.10.0

Docker was not available on the host, so only vepyr was measured. Every VEP-side result is a copy of
the 0.10.0 run directory `..._chr22_merged_v0100` on the harness branch (same host, VEP image, cache
and plugin data): `vep/` (VEP annotation), `B/*_vep_fork*.json` (VEP + filter_vep, through
`--reuse-filter-vep`), `B_sliced/` (tabix-sliced VEP baseline) and `A/*_filter_vep.json`
(filter-only experiment). `A/*_polars.json` were re-measured by `run_filter_only_polars.py`, which
requires the kept record counts to equal those of the 0.10.0 run.

The parity gate of the 0.10.0 run against VEP (`verify.json`) is carried over by `equiv.py`: for each
of the 18 queries and each output path (collect, VCF, Parquet), vepyr 0.11.0 must give the same
result as vepyr 0.10.0 (`equiv.json`: all 18 queries equal). A first attempt failed on the Parquet
schema (0.11.0 adds the column `_vcf_raw_info`); `equiv.py` now compares the columns of the 0.10.0
frame and records the extra column.

## Not included

- VCF outputs and inputs (`workers_chr*/*.vcf.gz`, `workers_chr*/input/*.vcf.gz{,.tbi}`, about
  370 MB) and `__pycache__/`.

## JSON bundles

`A/`, `B/`, `B_sliced/`, `C/` and `vep/` (one JSON file per query, mode and worker count) are stored
as one file each, `A.json`, `B.json`, `B_sliced.json`, `C.json` and `vep.json`, to keep the pull
request small (key = file name inside the directory). `scripts/make_supplement.py` reads the
directories, so restore them first with
`python performance-tests/paper-0.11.0/unpack_json_bundles.py A.json B.json B_sliced.json C.json vep.json`.
